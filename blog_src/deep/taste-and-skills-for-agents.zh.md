Agent skill 是一个带 `SKILL.md` 的文件夹，任务和它的描述匹配时，Agent 会去读它。对设计工作来说，这一点比听起来重要得多：关于间距、动效、哪些东西绝不能上线的判断，可以跨会话保留下来，而不是每天早上粘贴一大段提示词。这篇讲 skill 怎么加载、哪几类设计 skill 值得装、怎么组合才不打架，以及怎么写一个自己项目用的小 skill。

## skill 是怎么加载的

skill 开头是一小段 YAML 头，写 `name` 和 `description`，后面是 Markdown 格式的指令。支持 skill 的 Agent（比如 Claude Code）一开始只读取每个已安装 skill 的名称和描述；当前任务和描述匹配时，才加载完整正文。文件夹里的其他文件（参考文档、脚本、示例）只有正文指向它们时才会被读取。

这个设计对你有两个影响：

1. **描述就是触发条件。**"设计助手"永远不会在对的时候触发；"在本仓库新建或改版网页、组件时使用，强制执行我们的字号阶梯、间距和禁用样式"才会。
2. **正文可以长，但要分层。** Agent 每次都需要的规则放在 `SKILL.md` 里；长篇参考（完整 token 表、组件示例）放进单独文件，需要时再打开。

```markdown
---
name: house-ui
description: Use when creating or restyling any web page or UI component in this repo. Enforces tokens, spacing, motion limits and banned patterns.
---
# 本项目 UI 规则
1. 写样式前先读 tokens.css，绝不使用裸色值。
2. 间距来自 4px 刻度：4、8、12、16、24、32、48、64。
3. 每屏只有一个强调色，正文行宽最大 68ch。
4. 动效：150–250ms，ease-out，只动 transform/opacity，遵守 prefers-reduced-motion。
5. 禁止：文字渐变、玻璃拟态卡片、emoji 图标、正文居中。
组件示例见 examples.md。
```

## 四种职责，四类 skill

设计类 skill 可以分成四种职责。两个 skill 干同一件事，冲突就是这么来的。

1. **定方向**：在写代码*之前*运行。确定一种审美，并禁掉千篇一律的痕迹。例如 Anthropic skills 仓库里的 *frontend-design*，以及 *taste-skill*。
2. **手艺**：在*构建过程中*起作用，负责动效、微交互和细节判断。例如 *emil-design-eng*。
3. **走查**：在*初稿出来之后*运行，对照具体规则检查并报告问题。例如 *impeccable*、*baseline-ui*、*web-design-guidelines*。
4. **改版**：用于*已有*网站，先盘点现状再动手。例如 *redesign-skill*。

## 一套能用的组合，按步骤来

**第 1 步：每种职责只装一个。** 每个项目一个定方向、一个手艺、一个走查 skill 就够了。装两个定方向 skill，它们会争论页面该是杂志风还是粗野主义，Agent 最后会把两者平均成四不像。

**第 2 步：项目规则写进 AGENTS.md。** 通用审美 skill 不了解你的品牌。AGENTS.md 是放在仓库根目录的普通 Markdown 文件，编码 Agent 会读它获取项目说明。把硬规则写在这里，并明确写出它们优先于任何 skill：

```markdown
## 设计规则（优先于任何已安装的 skill）
- 品牌强调色是 #2563eb，不要引入第二个强调色。
- 标题用 Instrument Serif，正文用 Geist。
- 每个页面都必须同时有浅色和深色主题。
- 每页最多一个带动画的"高光时刻"。
```

**第 3 步：先跑定方向 skill。** 在写任何代码之前，让 Agent 先用文字提出方向：配色、字体搭配、布局想法、让页面被记住的那一个点。你来批准或修正。

**第 4 步：带着手艺 skill 去构建。** 让它处理 hover、焦点和过渡细节，同时 AGENTS.md 里关于动效的限制继续生效。

**第 5 步：走查，再按条目修。** 对结果跑走查 skill，要求输出带文件和行号的编号问题清单。小批量地修，不要一次全改。

## 常见坑

- **全部装上。** 十个设计 skill 就是十套建议在抢同一批决定。skill 多不等于审美好。
- **描述写得含糊。** 描述和你平时下达任务的说法对不上，skill 就永远不会加载，你还会以为它没用。
- **规则只说在聊天里。** 打过一次的规则下次会话就没了。同一句话说过两次，就该写进 AGENTS.md 或 skill。
- **没定方向就走查。** 对一个没有明确方向的页面做走查，只会得到一堆针对通用布局的鸡毛蒜皮。
- **不读就复制 skill。** skill 可以运行脚本。安装前先把文件读一遍，就像你会检查一个依赖包一样。

## 常见问题

**skill 能代替设计系统吗？** 不能。skill 告诉 Agent 怎么使用你的设计系统、要避开什么；token 和组件还是得真实存在，skill 只是指向它们。

**项目 skill 写多长合适？** 短到你自己愿意读完：`SKILL.md` 里 20 到 40 行规则，更长的材料放进链接的文件。Agent 无视某条规则，通常是因为它埋在一长串清单里，而不是清单太短。

**怎么知道 skill 生效了？** 给 Agent 一个应该触发它的任务，问它用了哪些 skill，再拿 skill 里的两三条规则核对产出。如果 skill 从不触发，就用你下达任务时的原话重写描述。

**不同的 Agent 能共用同一套 skill 吗？** 现在已有多个编码 Agent 会读取 skill 文件夹或 AGENTS.md。规则用纯 Markdown 写、不带特定工具的语法，同一套文件就能服务多个 Agent。具体读取位置以各自的文档为准。

**公开 skill 更新了怎么办？** 固定你审过的那个版本。把更新当作依赖升级：先看 diff，再决定是否接受。

## 我们的看法

skill 把审美从一段提示词变成了基础设施。大多数仓库里最有价值的，不是某个有名的公开 skill，而是一个 30 行、写着你自己 token 和"禁止"清单的项目 skill。从它开始，每种职责再加一个公开 skill；一旦发现某个 skill 给的建议你总在推翻，就把它删掉。

## 清单

- 每个 skill 的描述都和你平时的任务说法匹配
- 每个项目一个定方向、一个手艺、一个走查 skill
- 项目规则写在 AGENTS.md，并注明优先于 skill
- 写代码前先用文字确认方向
- 走查输出是带文件和行号的编号清单
- 每个安装的 skill 使用前都读过
