早期的设计转代码工具把画板翻译成一堆绝对定位的 div。在一个视口里看着没问题，换个尺寸就没法维护。新一代工具的思路不一样：Figma 的 MCP Server、Builder.io 的 Visual Copilot，以及跑在 Cursor 或 Claude Code 里的 Agent，读取的是*结构和变量*，并且能映射到你已有的代码。最后得到的是可复用代码还是一次性标记，现在更多取决于你喂给它什么，而不是用哪个工具。

## 核心思路：映射，而不是描摹

设计稿里有三类信息：**结构**（画板、自动布局、嵌套）、**决定**（颜色、间距、圆角、字体变量）和**组件**（按钮、输入框、卡片的实例）。描摹是照抄像素；映射则把结构变成 flex 和 grid，把决定变成你的 CSS 变量，把组件实例变成你自己的 `<Button>` 和 `<Input>`。映射出来的是能合并的 PR，描摹出来的只是一张用 HTML 写的截图。

## 第 1 步：让设计稿可读

模型只能映射明确写出来的东西。接入任何工具之前，先做这几件事：

1. **全部使用自动布局。** 没有自动布局的画板，模型只能根据坐标去猜 flex 方向、间距和对齐。猜出来的布局一缩放就坏。
2. **样式绑定到变量。** 填充色写死 `#2563EB`，模型拿到的只是色值；绑定到 `color/accent`，它就拿到一个可以映射成 `var(--accent)` 的名字。
3. **使用真正的组件实例。** 被分离（detach）的按钮只是一个带文字的矩形；Button 组件的实例才能告诉 Agent 该用哪个代码组件。
4. **按代码习惯命名图层。** "Frame 482"毫无信息；`PricingCard / Featured` 信息量很大。

## 第 2 步：把 token 导出成代码

设计决定只保留一个来源，再从它生成 CSS 变量。Design Tokens Community Group 定义了一种 JSON 格式，Style Dictionary 这类工具可以把它转换出来：

```json
{
  "color": {
    "accent":  { "$type": "color", "$value": "#2563eb" },
    "surface": { "$type": "color", "$value": "#ffffff" }
  },
  "radius": { "md": { "$type": "dimension", "$value": "10px" } }
}
```

```css
:root {
  --color-accent: #2563eb;
  --color-surface: #ffffff;
  --radius-md: 10px;
}
[data-theme="dark"] {
  --color-surface: #0d0f15;
}
```

Agent 看到 Figma 里的 `color/accent` 和 CSS 里的 `--color-accent` 同名，就会用变量，而不是粘贴色值。

## 第 3 步：发布组件注册表

注册表告诉工具：你的代码库里有哪些组件、怎么安装。以 shadcn/ui 为例，`registry.json` 列出你的组件，CLI 会把它们构建成可安装的 JSON 文件：

```bash
# 根据 registry.json 构建组件到 public/r/
npx shadcn@latest build

# 把你自己的组件安装到另一个项目
npx shadcn@latest add https://your-domain.com/r/pricing-card.json
```

Figma 的 Code Connect 从设计端解决同一个问题：它把 Figma 组件和代码组件关联起来，这样发给 Agent 的设计上下文可以直接说"这是 `<Button variant="primary">`"，而不是描述一个蓝色矩形。

## 第 4 步：接上桥梁

Figma MCP Server 会把选中画板的结构、变量和组件映射，提供给 Cursor、VS Code、Claude Code 这类 MCP 客户端。流程很短：

1. 只选一个画板，不要选整页。上下文越小，代码越好。
2. 让 Agent 读取选区的设计上下文，并在写代码之前先列出它打算用你的哪些组件。
3. 先修正这份清单。在 200 行代码出现之前改一句"用 `Card`，不要用 div"，成本低得多。
4. 再让它生成，然后像审普通 PR 一样审 diff。

Builder.io 的 Visual Copilot 从 Figma 插件出发，走的是类似的路，也能映射到你的组件。无论用哪座桥，质量上限都由前 3 步决定。

## 第 5 步：像审新人的 PR 一样审生成代码

生成的界面通常默认状态是对的，边界情况是错的。每次都要检查：

- **空、加载、错误状态。** 设计稿通常只画了顺利的那条路。
- **长内容。** 贴一个 60 字符的名称和一段德语翻译，看换行和截断。
- **比设计稿最小画板更窄时**的响应式表现。
- **写死的数值。** 在 diff 里搜应该是 token 的色值和像素值。
- **无障碍。** 按钮是 `<button>`，输入框有标签，焦点可见，对话框会锁定焦点。

```bash
# 对生成的 diff 做快速检查
git diff | grep -nE '#[0-9a-fA-F]{3,6}\b'      # 裸色值
git diff | grep -nE '\b[0-9]{2,}px\b'           # 魔法像素值
git diff | grep -n 'onClick' | grep -n '<div'   # 可点击的 div
```

## 常见坑

- **一次转整页。** 上下文过大，模型开始自己编结构。应该一个画板一个画板地来。
- **分离的实例。** 画板里只要有一个被分离的组件，就会产出一段永远不会随组件库更新的一次性代码。
- **token 有两个来源。** Figma 变量和 CSS 变量一旦不一致，Agent 会忠实地复现这种不一致。
- **跳过"先列清单"这一步。** 直接要代码，你就得审 300 行，而不是 10 行的组件清单。
- **期待像素级一致。** 映射出的代码会差几个像素，因为它用的是你的间距刻度。这恰恰是目的。

## 常见问题

**小项目值得这么做吗？** 如果总共不到五个页面，可以跳过注册表，直接把 token 文件和组件清单给 Agent。整套流水线的回报，出现在多人或多个 Agent 持续几个月做页面的时候。

**设计稿很乱又改不了怎么办？** 那就别直接从设计稿转。先让 Agent 用文字描述画板（分区、组件、内容），你修正这份描述，再根据描述和你的组件库生成。一份干净的描述胜过一个混乱的文件。

**该选哪座桥？** 选设计师已经在用、并且能读到你组件映射的那一个。桥本身没那么重要，重要的是设计稿里有没有变量、自动布局和组件实例。

**怎么衡量效果？** 统计生成代码有多少能原样通过评审，以及评审者需要把多少裸数值换成 token。随着注册表变大，这两个数字应该每周都在改善。

## 我们的看法

把注册表和 token 流水线当作基础设施，而不是一次性工作。第一个页面会慢一些，因为你在建立映射；之后每个页面都更便宜，因为 Agent 会复用它们。跳过这一步的团队，得到的是很快的初稿和永远很慢的维护。

## 清单

- 画板使用自动布局，图层命名有意义
- 填充、间距、圆角都绑定到变量
- token 已导出为同名 CSS 变量
- 组件已发布到注册表，或用 Code Connect 关联
- Agent 先列组件清单，再生成代码
- diff 检查了状态、长内容、色值和无障碍
