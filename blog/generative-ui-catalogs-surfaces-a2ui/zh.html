两年来，「生成式界面」大多意味着一个偶尔在气泡里画张图表的聊天机器人。这周它长大了。10 月 29 日，CopilotKit 大幅升级了它的生成式界面层：一个 70 个组件的标准目录，让智能体把界面渲染到你真实页面上指定区域的 surface（页面区域），以及让文字和组件在同一条回答里一起流式输出的 Markdown 模式。底层是 A2UI，由 Google 发起、CopilotKit 等参与贡献的开放协议，1.0 规范现在处于候选版本。两天前，Google 的 A2UI 团队还发布了一种让模型更快写出 A2UI 的方式。放在一起看，这几次发布把一个重要决定从工程师手里交给了设计系统的负责人：智能体能用哪些组件、用在哪里、带什么属性。

这周发布了什么

  • 70 个组件的标准目录。布局、文字、表单输入、表格、图片、视频、图表（基于 Recharts）和地图（基于 MapLibre），外加链接预览、引用、商品卡片、追问建议等现成区块。CopilotKit 说其中 18 个是 A2UI 的基础组件，另外 52 个是它自己的。
  • 你自己的组件，带类型。用 createGenerativeUI 注册：每个组件有一段描述，智能体靠它决定什么时候用；还有一个属性 schema（Zod、Valibot 或 ArkType）。三个开关决定你的目录和标准目录怎么共存：extends 两者都保留，omit 移除组件、让智能体根本看不到，overrides 用你的组件替换标准组件。
  • 聊天框之外的 surface。用 GenerativeUISurface 包住页面上任意区域，给它一个 id、一段说明这里该放什么的文字、允许使用的组件列表，以及一个兜底内容（你平时手工做的界面）。智能体只有在该区域出现在屏幕上时才看得到它；不在允许列表里的组件会被拒绝，并告诉智能体原因。
  • 两种流式模式。工具模式（默认）通过工具调用发送界面，逐块渲染；Markdown 模式让智能体直接把界面写进回复。滑块、实时数值和表单校验都在浏览器里运行，所以和生成的界面交互不额外消耗 token。
  • 防护与调试。每一块在渲染前都会对照目录检查，生成的界面不会在你的页面上执行代码，每个组件有自己的错误边界，Inspector 新增的面板会显示渲染了什么、拒绝了什么、模型看到的完整提示。在 A2UI 1.0 定稿之前，CopilotKit 把这些都标为实验功能。

为什么 A2UI 和设计师有关

A2UI 的核心思路很简单：智能体不发 HTML，也不发代码，而是发一份声明式描述，里面只能用客户端批准过的目录里的组件，客户端再用自己的原生组件渲染（已有 Angular、Flutter、Lit、React 和 Markdown 渲染器）。这样，目录就是智能体唯一的词汇表。10 月 27 日，Google 加入了可替换的「推理格式」：模型可以写 A2UI Express，一种逐行书写的紧凑语法，再由 SDK 编译成标准 A2UI 消息。Google 称它比直接写 JSON 最多少用 3 倍 token、延迟最多降 3 倍；如果只让一个小型决策模型在你预先设计好的版式之间挑选，速度还能快得多。对设计质量最关键的一点是：提示和编译器都从你的目录 schema 生成，所以这种格式描述不出目录里没有的组件或属性。10 月 30 日，项目还发布了第一个命令行工具，可以从目录 schema 生成带类型的构建器。

我们的看法

这是智能体搭界面的正确形态，而且它改变了「结果归谁负责」。当智能体只能从带类型的目录里组合，「符合品牌」就不再是写在提示里的愿望，而是系统本身的属性：如果目录里没有霓虹渐变按钮这个变体，智能体就根本输出不了。反过来，目录的每个弱点都会暴露出来。描述含糊（「一张卡片」），智能体就什么都用它；variant 属性是自由文本，就等于邀请它发明样式；surface 没有好的兜底，模型慢了或错了就会留下一个洞。所以手艺往上游移：设计师应该把组件描述写成使用规范，把属性类型收窄，并为每个 surface 设计空状态、加载中和出错状态，因为这些现在都是产品的一部分。两点提醒：CopilotKit 的 API 明确是实验性的，速度数字是厂商给出的最好情况，所以要锁定版本，在你自己的页面上实测。

清单：让智能体改不坏的组件目录

  1. 从窄开始。每个 surface 只给它需要的组件（components 或 omit）；商品行只接受商品卡片，不接受滑块。列表越短，提示也越短。
  2. 替换基础组件。用你自己的 Button、Card、Input 替换标准组件，让 token、圆角和焦点样式来自你的系统，而不是库的默认值。
  3. 把描述写成规则。写清什么时候用、什么时候不用、不用时换成什么。智能体每次运行都会读。
  4. 收窄属性类型。变体和语气用枚举，数字用数字类型，标签限制长度。自由字符串正是「发明样式」的来源。
  5. 先设计兜底内容。每个 surface 在智能体接手之前、以及放手之后，都应该显示你手工设计的真实界面。
  6. 设计中间状态。流式加载骨架屏、单个组件的出错兜底，以及智能体移除 surface 后这块区域的样子。
  7. 用户输入不能动。用户已经填写的值绝不能被智能体覆盖，确认你的配置做到了这一点。
  8. 用 token 定主题，测暗色模式。生成的页面应该和手工页面通过同样的对比度检查（正文 4.5:1）。
  9. 看被拒绝的记录。每周看一遍 Inspector 里被拒绝的内容：反复被拒，说明缺组件或描述有误导，而不是模型不行。
  10. 按页面选模式。固定版式更适合预先设计好的模板、由智能体挑选；自由组合留给真正多变的页面。

UI Hub 能帮什么

好的组件目录从有名字的数值开始：给智能体的设计 Token 讲了怎么把它们写下来，用 Lint 把智能体拉回你的设计系统 讲了事后怎么抓住一次性数值。智能体界面里聊天那一侧（步骤、工具调用、代码输出），见 shadcn Trace 与 AI Elements；智能体在页面上动手时的审批与打断模式，见智能体审批界面。决定目录里该放什么组件时，UI Hub 的组件页面是一份好用的清单。
