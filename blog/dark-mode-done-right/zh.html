直接反色，是做出糟糕深色模式最快的办法：纯黑背景、刺眼发光的饱和蓝、消失的边框、谁也看不见的阴影。Apple 的人机界面指南和 web.dev 都把深色模式当作一次独立的设计，而不是一个滤镜。这篇讲：让两套主题成本很低的 token 结构，表面、颜色和对比度的规则，没有白屏闪烁的分步实现，以及上线前要检查什么。

从语义 token 开始

让深色模式可控的关键决定只有一个：按角色给颜色命名，而不是按色值。组件只用 --bg、--surface、--ink、--muted、--line、--accent，每套主题给这些角色赋值。组件永远不需要知道自己在哪套主题里。

:root, [data-theme="light"] {
  color-scheme: light;
  --bg: #f5f6fa;  --surface: #ffffff;  --raised: #ffffff;
  --ink: #0a0c14; --muted: #4a5164;    --line: rgb(10 12 20 / .10);
  --accent: #2563eb;
}
[data-theme="dark"] {
  color-scheme: dark;
  --bg: #06070b;  --surface: #0d0f15;  --raised: #151924;
  --ink: #f3f5fb; --muted: #a6adbf;    --line: rgb(255 255 255 / .10);
  --accent: #67e8f9;
}
.card { background: var(--surface); color: var(--ink); border: 1px solid var(--line); }

如果代码里到处是 #fff 和 text-gray-900，做深色模式的第一步就是把它们换成角色变量。只要给 Agent 一张角色对照表，这种机械重构它做得很好。

表面与颜色的规则

  1. 近黑，而不是纯黑。 在很多屏幕上，纯 #000 背景配白字会让光晕（亮字周围的发光）最明显。#06070b 这样很深的蓝灰看起来就是黑色，眼睛更舒服。
  2. 近白文字。 正文用 #f3f5fb 而不是 #ffffff；纯白最多留给少量强调。
  3. 用亮度表达层级。 浅色模式靠阴影分层；深色模式里阴影几乎看不见，所以越高的层越亮：背景、表面、浮层依次变亮。Material 的深色主题指南也是这个思路。
  4. 强调色降饱和、提亮。 在白底上好看的饱和 #2563eb，放在近黑底上会"抖"。深色主题选一个更亮、饱和度更低的强调色，并分别检查它作为文字和作为按钮底色的效果。
  5. 边框更重要。 阴影弱了，常常要靠一条 1px 半透明线把卡片和背景分开。
  6. 图片和插图。 白底的 logo 和示意图会变成刺眼的白块。提供深色版本，或者放在中性底色上。

两套主题都要查对比度

WCAG 要求普通文字对比度至少 4.5:1，大字和界面组件至少 3:1。在两套主题里都要检查次要文字、占位文字、禁用状态和链接。最常见的问题是：次要灰色在白底上合格，在近黑底上不合格，或者反过来。

分步实现切换

第 1 步：尊重系统设置，记住用户选择。 默认跟随 prefers-color-scheme，允许用户覆盖，并保存覆盖结果。

第 2 步：首次绘制前设定主题。 在 <head> 里放一小段内联脚本，避免加载时白屏闪烁：

<script>
  try {
    const saved = localStorage.getItem("theme");
    const sys = matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "light";
    document.documentElement.dataset.theme = saved || sys;
  } catch (e) {
    document.documentElement.dataset.theme = "light";
  }
</script>

第 3 步：设置 color-scheme。 它告诉浏览器用对应主题渲染表单控件、滚动条和默认画布。不设置的话，深色页面上会出现浅色滚动条。

第 4 步：考虑 light-dark()。 现代浏览器支持 CSS 的 light-dark() 函数，会根据当前 color-scheme 选值。适合零散的数值：border-color: light-dark(#e5e7eb, #262a35);。

第 5 步：接好切换按钮。 更新 data-theme、保存选择，同时更新 aria-pressed 或按钮文字，让读屏用户知道当前状态。

五分钟深色模式走查

在真实手机上把亮度调低、在笔记本上把亮度调满，分别用深色模式打开页面。看四件事：文字边缘发光或发虚（对比过强，常见于纯白字配纯黑底）、卡片融进背景（缺边框或亮度层级）、强调色发抖，以及任何白色方块（从没做过主题的图片、嵌入或代码块）。然后用按钮切换主题并刷新：页面应该保持你选的主题，而且没有闪烁。

常见坑

  • 用滤镜反色。 filter: invert(1) 会把照片和品牌色也一起反掉。
  • 忘了第三方嵌入。 代码块、地图、图表、iframe 经常停留在浅色。给它们做主题，或者加一圈边框。
  • 只靠阴影分隔。 深色模式里阴影会消失；加边框或亮度层级。
  • 只测一套主题。 每次截图走查、视觉测试和设计评审都要包含两套。
  • 主题闪烁。 在框架的 effect 里、水合之后才设置主题，每次加载都会先闪一下错误的主题。

常见问题

深色要不要做默认？ 默认跟随系统设置。偏好深色的用户通常已经在操作系统层面设置过了，偏好浅色的也一样。手动切换按钮覆盖其余情况。

Figma 里需要单独画一套深色设计吗？ 需要为每个角色 token 定义深色数值，并在深色下检查关键页面。只要组件用的是角色 token，就不需要把每个页面重画一遍，主题切换会完成这件事。

图表和数据可视化怎么办？ 图表配色需要单独的深色版本。在白底上能区分的颜色，在近黑底上可能会混在一起。两套主题下都要把分类色并排检查，并且永远不要只靠颜色区分数据系列。

怎么防止两套主题逐渐走样？ 在两套主题下都跑视觉回归截图，出现意外变化就让构建失败。把"在某一套主题里看起来不对"的组件当作 bug，而不是锦上添花的打磨项。

"暗淡"或高对比算不算第三套主题？ 如果用户需要，就算。角色 token 结构让它只是第三列数值。在发明自定义选项之前，先尊重 prefers-contrast。

我们的看法

NN/g 的研究显示，用户对深浅色的偏好各占一部分，而且因场景而异，所以两套都要做，并记住用户的选择。第二套主题的成本几乎全在 token 结构上：角色定对了，深色模式就只是第二列数值。UI Hub 给每个组件同时保存浅色和深色预览截图，正是这个原因；只在一套主题里好看的组件，只完成了一半。

清单

  • 组件只用角色 token，没有裸色值
  • 近黑背景、近白文字，越高的层越亮
  • 深色专用强调色分别作为文字和底色检查过
  • 两套主题都验证了 4.5:1 文字对比度
  • 首次绘制前设定主题，并设置了 color-scheme
  • 尊重系统偏好，并记住用户的覆盖选择
